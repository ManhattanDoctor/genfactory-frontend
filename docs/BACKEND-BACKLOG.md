# Что перенести с frontend в gnosis позже

Живой список для обсуждения. Пункты ниже — предложения, а не изменения согласованного API. Изменения выполняются только после согласования конкретного пункта; актуальный статус реализации указан в его разделе. При добавлении клиентского обходного решения обновлять этот документ: текущее поведение, ограничение, серверная возможность и критерий готовности.

Список фиксирует потребности клиента. Перед реализацией идей нужно проверить существующие сервисы gnosis: отсутствие интеграции на фронте само по себе не означает отсутствие серверной возможности. Недостающие контракты следует дополнять, а не создавать дубли существующих сущностей.

Статусы: **локально реализовано**, **частично на frontend**, **идея**. Приоритет отражает пользу для надёжности и совместной работы, а не согласованный порядок реализации.

## Правила миграции локальных данных

1. Не загружать содержимое localStorage целиком: передавать только поля конкретной версии формата. SID, токены и временное состояние не мигрируют.
2. Привязывать данные к текущему владельцу; проверять доступ к каждому файлу и беседе на сервере. Идентификатор пользователя из JSON не является подтверждением владельца.
3. Импорт делать идемпотентным, с отчётом о конфликтах и явным выбором пользователя при замене. Локальную копию удалять только после подтверждённого сохранения и чтения серверной версии.
4. Старые локальные снимки запусков считать клиентскими записями предпочтений, а не доказательством фактической модели, результата или списания. Не создавать на их основе фиктивные финансовые записи.
5. Оставить клиентскую валидацию и проверки для удобства пользователя; авторитетные проверки, права и ограничения выполнять на сервере.

## Что оставить на frontend

Отступы и адаптивность, просмотр/сравнение изображений, выбор референсов и их порядок до отправки, локальный буфер редактирования, доступность интерфейса, поиск по уже полученному небольшому каталогу. Переносить нужно постоянные данные и гарантии выполнения, а не всю логику интерфейса.

## Подтверждённый инцидент: беседа 49, 02.11.2026

В 09:46:56 МСК создан дизайн чашки, файл 97. В 09:48:19 пользователь отправил запрос на перенос дизайна на чашку: файл 97 присутствует и в `files`, и в инструкции `fileIds`. В 09:48:30 сохранён ответ ассистента «Не удалось запустить генерацию из-за технической ошибки инструмента», без файлов. Беседа при этом имеет статус LOADED. Точная первичная причина по доступным данным не установлена.

Локальный frontend использует API :3015. Проверены локальные логи и контейнер gnosis-api на 178.208.65.196: диагностической записи об этом вызове в просмотренных логах нет. GET прогресса conversation49 после завершения возвращает 404. В текущем `AiTool.erroredHandler(output)` переданный объект ошибки не сохраняется, публикуется только ERRORED; история ConversationMessage не содержит аргументов вызова и первичной ошибки инструмента.

**Нужна приоритетная диагностика запусков:** сохранять call ID, conversation/message/run ID, имя инструмента, безопасные аргументы, выбранную модель, время, код/тип ошибки, очищенное от секретов сообщение и provider request ID, если он доступен. Отдельно хранить итог работы инструмента и итог ответа ассистента: LOADED-беседа не должна интерпретироваться как успешная генерация. Не определять успех или причину ошибки по произвольному тексту LLM. При воспроизведении сначала использовать проверки без платного запуска; повтор генерации не выполнять автоматически.

### Повтор с локальной диагностикой

По отдельному разрешению пользователя 02.11.2026 добавлено opt-in логирование `GNOSIS_TOOL_DIAGNOSTICS=1`, локальный API перезапущен. Исходный пользовательский запрос 166 повторён одним POST в ту же беседу 49, с референсом 97 и настройками gpt-image-2 / 1024×1024 / medium / opaque. Повтор успешен: новое сообщение пользователя 168, ответ 169, изображение 98. В логе IMAGE: `isDrawNew:false`, `fileIds:[97]`, результат `edited`, status success. Первичная ошибка не воспроизвелась; её причина остаётся неизвестной. Успешный повтор не является доказательством исправления исходного дефекта. Постоянная диагностика запусков и корректное различение статуса беседы/генерации остаются в списке.

### Явный выбор исходника для продолжения беседы

Frontend показывает выбранные референсы до отправки, предлагает последний результат беседы (с поиском по страницам сообщений) и требует отдельного выбора «Создать с нуля». Выбор не запускает генерацию. Перед отправкой проверяется доступность файлов; устаревшая инструкция Genfactory заменяется через текущий PUT беседы, без замены пользовательских настроек.

В дальнейшем стоит передавать намерение отдельным структурированным полем запуска (`references` / `fromScratch` / `conversationContext`), а не только текстом сообщения. Backend должен проверять фактические аргументы IMAGE/VIDEO: выбранные исходники не должны исчезать из вызова инструмента. Нужны сохранение выбранного режима и исходников вместе с запуском и чтение фактически использованных файлов. Сейчас frontend гарантирует состав отправленного сообщения, но не может принудительно обеспечить поведение LLM внутри инструментального вызова.

02.11.2026: локальная диагностика теперь включена по умолчанию в development (`LOGGER_LEVEL=ALL`, tool diagnostics), чувствительные значения редактируются в логах. Разрешённый повтор беседы 52 успешно создал файл 108 с референсом 90, стоимость 8,1585 ₽. Причина первоначальной ошибки не установлена: исходный диагностический лог отсутствует. Постоянная серверная история вызовов инструментов остаётся отдельной задачей.

## File browser (2026-11-02)

The React library and attachment picker share `FileBrowser`, backed by existing file APIs. No backend changes in this iteration.

- Add an atomic directory move operation: existing `FileService.edit` updates only the directory row, leaving descendant paths unchanged. Until available, frontend moves only files/links. Validate parent ownership, prevent cycles, update descendant paths transactionally and notify affected clients.
- Implemented locally: `FileEditController` returns fresh metadata; edits validate destination ownership and normalize tags.
- Implemented locally: multipart upload accepts directory and tags in one request; shared file creation applies and validates these settings.
- Expand list API with effective media type for links and folder-aware search/breadcrumb metadata; frontend currently filters media by MIME, resolves the target on selection, and searches by name across all folders.

### File output context implemented locally

Conversation `fileOutput` stores default directory and tags. Shared `IFileAddContext` carries a snapshot through tools/graphs and persists in video jobs. Existing conversation/message file relations are reused. File `origin` contains creation kind, operation ID and historical source IDs (kept when inputs are deleted; not foreign keys). No semantic AI tagging or extra model requests.

Completed generated results fall back to root when the destination disappeared, marked by origin.directoryFallback and explained in the viewer. Source IDs remain historical when inputs disappear after execution started. New requests with inaccessible destinations still fail before execution. Reliable parent conversation recovery after process restart remains separate from durable video result storage. Directory-wide move remains deferred.

### Unified file responses and tag search — implemented locally

- FileService enriches file responses with previews for upload, buffer upload, link creation, read, edit and list; conversation/message attachments use the same batch path. Metadata edit returns fresh data.
- GET /api/fileTag provides paginated, case-insensitive own-tag suggestions with distinct file counts and literal prefix search. Even administrators receive only their own tags.
- Existing file-list INCLUDES_ALL / INCLUDES_ONE_OF tag filters normalize whitespace/case without a data rewrite; new frontend supports both modes and clickable card tags. Filters search across folders and server pages.
- No separate tag entity/table yet; tags remain user-managed file metadata. Automatic semantic tagging is not enabled.

### Audio editor — implemented locally (2026-11-03)

TTS and STT use existing conversations, per-tool model settings and the server model catalog. STT now accepts video directly through MediaSplitCommand; FFmpeg checks for an audio track before recognition. Supported persisted TTS encodings are shared by the schema and tool. No new tables or audio-generation endpoints. Live verification subsequently added authenticated file text/content reads to avoid storage CORS; see BACKEND-CONTRACT.md.

Remaining backend work:

- Structured transcription result with segments, timestamps and optional speakers, then SRT/VTT export. Current provider tasks return plain text.
- A deterministic execution API for a selected tool within a conversation, avoiding an extra assistant interpretation step for exact TTS/STT operations. The editor currently uses the established conversation mechanism.
- Durable recovery for interrupted non-video tasks and explicit tool outcome in history; do not infer success solely from conversation LOADED.
- Reliable preflight cost estimate including assistant overhead. UI currently links to actual balance history and does not invent an estimate.
- Per-model voice catalogs and verified encoding capabilities for providers whose schema currently exposes a free-form voice string. Do not maintain provider voice lists in the frontend.
- Dubbing/mixing with video and subtitle timing are separate media operations; they are not implemented in this iteration.

## GP-VIDEO-01. Полноценный анализ видео в Generate Prompt

**Статус:** запланированная доработка, не реализована. Добавлено по прямому запросу пользователя 2026-11-05. Порядок работ и изменения backend необходимо согласовать отдельно; запись в списке не является разрешением менять API.

**Цель:** пользователь выбирает видео из библиотеки, задаёт, что сохранить и для чего нужен промпт, и получает описание с учётом действия, последовательности событий и движения камеры.

**Как у дизайнера, по коду:** браузер принимает MP4/WebM/MOV до12МБ, всего до4материалов, и передаёт видео целиком как data URL. Сервер `file_prompt.py` проверяет формат/размер и совместимость анализатора. В режиме «Авто» для видео выбирает модель, обозначенную в прототипе как Gemini3.8Flash; несовместимый ручной выбор отклоняется. В сообщение модели добавляется `video_url`, а не три предварительно извлечённых кадра. Возвращается проверяемый структурированный ответ: готовый промпт либо уточнение/блокировка, наблюдения по исходникам, ограничения и вопросы. Это подтверждено чтением кода, а не платным запуском прототипа; доступность названной модели нужно проверять по действующему каталогу.

**Сейчас у нас:** новый `/prompt` работает только с изображениями. Прежний механизм в общей текстовой форме извлекает три кадра на10/50/90%длительности, не анализирует звук и непрерывное движение. Он не является эквивалентом полноценного анализа видео.

**Что сделать:**

1. Проверить существующие Gnosis-провайдеры и контракты на передачу видео модели; использовать имеющиеся возможности, не создавать дублирующий сервис без необходимости.
2. Подключить подтверждённую видеоаналитическую модель к каталогу с корректными capabilities и лимитами. Установить отдельно, анализируется ли звуковая дорожка; не обещать это по одному факту передачи видео.
3. Передавать существующий пользовательский файл из библиотеки с проверкой доступа, формата и размера. Не подменять полный анализ выборкой трёх кадров без явного указания ограничения.
4. Добавить видео в интерфейс Generate Prompt, совместимый выбор «Авто», валидацию ответа и привязку наблюдений к исходнику. Сохранять настройки, исходники и результат через существующие сущности, где это возможно.
5. Проверить реальным коротким роликом с заметным изменением действия во времени: корректность промпта, наблюдений, ограничений, сохранение после перезагрузки и ручную передачу в генератор без автоматического запуска медиа.

**Критерий готовности:** видео принимается и реально передаётся совместимой модели; результат отражает проверяемые события ролика, а ограничения анализа указаны честно. Несовместимые материалы/модели отклоняются до платного вызова, ошибки не запускают автоматическую повторную генерацию. Стоимость и задержка проверены на недорогом контрольном примере.
